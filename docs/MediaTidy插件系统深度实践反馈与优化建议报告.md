# MediaTidy 插件系统深度实践反馈与优化建议报告

> **反馈背景**：
> 本反馈由一线插件开发者在深度开发并落地两款生产级插件（**「STRM 重复扫描」** `media.dup-scan` 与 **「影视查重」** `media.series-dedup`）过程中，历经全链路实机部署、逆向追踪与端到端闭环验证后总结提炼而成。
> 
> MediaTidy 的插件体系采用了非常现代且优秀的架构设计（如纯静态 AST 驱动的前端、多进程隔离的 Python Worker、精细的 Capability 权限模型与响应式数据绑定）。但在实际工程落地与用户日常使用中，仍存在一些影响体验的深层问题与死锁痛点。以下建议旨在助力 MediaTidy 插件生态更加健壮、易用、友好。

---

## 一、 核心痛点与致命性问题（建议高优先级修复）

### 1. 插件升级导致配置（Storage）丢失，无跨升级继承机制
- **当前现象**：
  当用户通过 Git 或 ZIP 升级已安装的插件时，宿主会为新构建生成全新的 `instance_id`。然而，MT 底层的 KV Storage（`ctx.mt.storage`）是直接以 `instance_id` 作为数据所有者（owner）隔离存储的。
- **负面影响**：
  用户在工作台精心配置的目录路径、选定的整理方案、分差阈值、甚至长期维护的白名单/保护组名单，**只要插件一升级，全部设置瞬间被清空回默认值**！用户每次升级插件都必须全部重新配置一遍，使用体验非常糟糕。
- **优化建议**：
  - **建议将 Storage 的持久化作用域与 `plugin_id` 绑定**（或默认提供基于 `plugin_id` 的跨版本继承机制），而非仅与单次安装的 `instance_id` 强绑定；
  - 在升级流程（`upgrade/install`）完成切换时，宿主自动将旧实例的 KV Storage 数据迁移或复制给新实例。

---

### 2. 初次从 Git 安装时权限折叠面板默认收起，导致空权限引发安装失败
- **当前现象与深层链条**：
  在 MT 前端“从 Git 安装插件”的模态弹窗中，底部的“权限配置”折叠面板默认是**收起（折叠）状态**。绝大多数普通用户在点击“检查”通过后，会直接顺手点击“安装”按钮，根本不会特意展开折叠面板去手动勾选每一个权限。
- **连锁事故**：
  1. 用户直接点击“安装”后，前端提交给后端的授权数据中 `capabilities` 实际为**空列表 `[]`**（没有任何能力被激活）；
  2. 宿主拉取代码并启动 Worker 执行 `on_init(ctx)` 生命周期；
  3. 99% 的插件作者都会在 `on_init` 中写入初始配置（如调用 `ctx.mt.storage.set`），或者读取文件系统。此时由于 `storage` 权限未被勾选，宿主拦截器当场抛出：
     `插件没有此能力或资源的授权`
  4. 最终导致整个插件在安装阶段直接变红崩溃（Status: error），用户满头雾水，误以为插件代码损坏！
- **优化建议**：
  - **前端默认全选**：在安装弹窗中，前端应默认勾选插件在 `manifest.permissions` 中声明的所有必要能力（如 `storage`、`files.read` 等），用户如果需要限制才主动展开取消勾选；
  - **安装期保底机制**：宿主在执行安装初期的 `on_init` 时，至少默认放行 `storage` 基础存储能力，确保插件能够平稳完成初次初始化。

---

### 3. 配置校验（`validate_config`）失败导致插件永久置为 `error` 状态，陷入死锁
- **当前现象**：
  当插件的 `validate_config` 校验返回错误，或者清单发生微调时，宿主会将插件置为 `status: error`（例如提示：`配置校验失败：插件清单完整性校验失败`）。
- **死锁闭环**：
  1. 插件一旦进入 `error` 状态，前端访问工作台（`GET /api/plugins/{id}/ui`）会被宿主硬拦截并直接返回 400 `NOT_READY`，导致用户**根本打不开工作台**去修正配置；
  2. 此时若尝试在管理页面通过 API/UI 保存新配置，宿主会先执行该插件的校验，由于当前处于错误态或旧配置依然不合法，保存操作再次被拒绝；
  3. **结果**：陷入死锁！用户既无法进入工作台修改，也无法通过常规方式拯救配置，最终只能被迫“卸载插件”，导致所有配置与历史扫描数据全部被物理摧毁。
- **优化建议**：
  - 即使插件处于 `error` 或 `config_invalid` 状态，也应允许渲染 `get_page`，或者自动切换至“安全修复模式”视图，允许用户在工作台中修改配置并重新提交校验；
  - 允许在管理面板中“强制覆盖保存合法配置”，打破死锁状态。

---

### 4. 错误信息泛化与黑盒化（`OPERATION_FAILED`）
- **当前现象**：
  在插件开发过程中，高频遇到 API 返回：
  ```json
  {"code": 400, "data": {"error": {"code": "OPERATION_FAILED", "message": "操作未完成，请查看 MT 中对应业务的状态"}}}
  ```
- **实际排查出的真实底层原因**：
  - 场景 A：清单 `plugin.json` 中的 `triggers` 写成了对象字典 `{}`，而 Go 结构体要求是列表 `[]`；
  - 场景 B：`permissions` 列表中包含了一个系统未定义的能力名称（如 `files.inspect`）；
  - 场景 C：前端组件 AST 中某个组件传递了不在枚举白名单中的属性（例如 Button 加了 `size="sm"`，或 Grid 的 `columns` 大于 4）；
  - 场景 D：SQLite 数据库中残留了一条中断的 `installJob` 记录，结果导致整个 `GET /api/plugins` 列表接口直接全部 400 崩溃。
- **优化建议**：
  - 抛出结构化的具体错误明细（例如：`ManifestError: field 'triggers' expected array, got object` 或 `ASTValidationError: Button does not support prop 'size'`）；
  - 单个插件的元数据或历史构建异常，不应级联拖垮整个 `/api/plugins` 插件列表接口，建议做容错降级（将异常插件标记为 `corrupted`，其余正常插件正常列出）。

## 二、 前端 AST UI 框架的体验与组件扩展建议

MediaTidy 基于纯静态 AST 树驱动前端界面的理念非常出色（安全、无跨站脚本风险、响应式清晰），但在实际排版与交互中有几个明显的局限：

### 1. 缺乏轻量级的「目录选取器」（FolderPicker）
- **痛点**：
  目前系统只提供了 `ui.FilePicker()`。这是一个铺满一整屏的文件系统树，用来做全量片源勾选很合适；但如果在配置卡片里仅仅希望用户**“指定一个扫描根目录”**或**“指定一个转移目标目录”**，把巨大的 FilePicker 嵌在页面中显得极其突兀笨重，严重破坏页面排版。
- **建议**：
  新增轻量级目录选取组件（如 `ui.DirectoryPicker` 或 `ui.Input` 支持 `type="directory"`），呈现为“输入框 + 右侧小文件夹图标”，点击弹出悬浮模态框选目录，选定后自动填入路径。

### 2. 按钮（Button）缺少内置的 Loading 态与防重触发机制
- **痛点**：
  在耗时操作（如启动查重扫描、提交批量任务）中，由于前端没有按钮级的 `loading` 旋转动画属性，开发者只能通过 `disabled=ui.ref(...)` 配合顶部 Alert 来提示。如果用户快速连续点击，或者通过 `onClick` 试图先设 `state.is_running=true` 再调 action，极易发生状态冲刷引发的闪烁或重复请求。
- **建议**：
  `ui.Button` 增加原生 `loadingBind` 属性（如 `loadingBind="run.status.is_running"`），点击后按钮内部原生展示 Spinner 旋转动画并自动置灰防重复点击。

### 3. 表单组件属性与数据绑定的完善
- **痛点**：
  - 目前 `ui.Input` 不支持直接赋默认值/回显当前值（在 AST 中写 `value` 会直接触发 400 校验错误），必须完全依赖 `bind`；但在跨升级场景下，如果 storage 暂时为空，输入框无法友好显示默认建议值；
  - `ui.Table` 内部单元格对嵌套组件支持有限，列宽无法显式指定像素或百分比，容易出现较长路径或标题挤占按钮操作列的情况。

## 三、 权限系统（Grants & Capabilities）与生命周期建议

### 1. 权限升级时的自适应裁剪与平滑过渡
- **痛点**：
  当插件版本升级并精简了权限时（例如旧版申请了 6 个权限，新版优化后只申请 4 个），如果前端在调用 `upgrade/install` 接口时沿用了旧的权限列表，Go 宿主会抛出：`插件没有此能力或资源的授权` 强行阻断安装。
- **建议**：
  在安装和升级时，宿主应对传入的授权列表做 `intersect`（交集处理）：自动过滤掉新版清单不再声明的多余能力，而不是直接抛错阻断升级流程。

### 2. Python Worker SDK 方法的传参规范与类型提示
- **痛点**：
  - `ctx.mt.storage.set` 必须严格使用关键字传参 `set(key=..., value=...)`，如果按常规习惯写 `set("k", "v")` 会直接抛出 `TypeError: takes from 1 to 2 positional arguments but 3 were given`；
  - `ctx.mt.tasks.wait` 调用成功后，必须立即 `return {"waiting": True}` 释放进程，若继续调用 `ctx.mt.log` 会抛出 `FLOW_WAITING` 致命错误。
- **建议**：
  在 `mt_plugin` SDK 中补全完整的 Python Type Hints（`.pyi` 存根文件）与更宽松的参数适配（同时兼容位置传参与关键字传参），降低第三方开发者的心智负担。

## 四、 存储根目录（Roots）与多用户通用生态建议

### 1. 强化基于 `ctx.mt.files.roots()` 的动态感知，杜绝私有目录硬编码
- **痛点**：
  在开源社区中，第三方开发者写插件时极易把个人 NAS 的绝对路径（如个人网盘挂载点、私有命名目录）写死在插件的默认配置或业务逻辑中。一旦其他用户安装，默认路径与自身环境冲突，插件无法正常运行，甚至导致任务提交至不存在的目录。
- **优化建议**：
  - **倡导最佳实践**：在官方开发文档中明确定调，插件获取目录时应强制优先调用 `ctx.mt.files.roots()`，动态感知当前用户实际授权的根目录列表，并以真实挂载根作为默认路径；
  - **宿主注入标准环境变量/宏**：建议宿主向插件上下文（`ctx`）直接注入通用目录宏（例如 `ctx.roots.primary` 或 `ctx.roots.strm`），使开发者无需硬编码任何路径即可实现跨平台、跨用户的即插即用。

---

## 五、 总结与结语

MediaTidy 的插件体系构想宏大、架构底座非常优秀，特别是在安全性、沙箱隔离以及与 MT 核心能力（整理方案、评分规则、任务队列）的打通上展现出了极高的工程水准。

如果在接下来的迭代中能够重点解决：
1. **配置的跨升级继承（Storage 绑定 plugin_id）**；
2. **初次安装权限面板默认勾选必要能力（避免安装期被拒报红）**；
3. **错误状态下的可维护性（避免配置死锁）**；
4. **更精确明朗的报错提示（细化 OPERATION_FAILED）**；
5. **补充轻量目录选取器与按钮 Loading 态**；
6. **提倡动态感知 Roots 挂载点，消除硬编码私有目录**；

MediaTidy 的插件生态必将吸引更多优秀开发者参与，生态体验也必将迈上全新的台阶！
