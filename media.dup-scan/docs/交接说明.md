# media.dup-scan 交接说明

换对话后先读这一页，再动手。

## 一、这是什么

MediaTidy（MT）插件，id **`media.dup-scan`**，中文名「STRM 重复扫描」。
作用：在**单个 tmdb 作品目录内部**找出重复的 strm，用 MT 自己的评分规则判哪个版本该留、哪个该删。

**只报告，不删除任何文件。** 这一点在代码和权限两层都锁死了：

- manifest 只申请 `files.read / storage / rules.read / organize.read / tasks.read / tasks.wait`，
  **没有** `files.delete`、`files.write`、`strm.run`、`strm.cleanup`；
- 全项目 grep `files.delete|files.write|os.remove|os.unlink|shutil.rmtree|os.rename` **零命中**。

用户明确说过「先别真实删除，我怕你删错了」（m23839）。

## 二、需求边界（用户 m23439 定，已确认）

| 问题 | 答案 |
|---|---|
| 重复在哪里找 | **只在一个 tmdb 作品目录内部**；跨目录交给别的插件 |
| 动作 | 只报告不删除 |
| 评分规则 | **运行时从 MT 取**，插件内不写死 |
| 连集包重叠（`S01E01-E08` vs `S01E01`） | 完全不处理也不显示 |
| 跨目录同 tmdb（乘风 vs 乘风破浪的姐姐） | 不管 |
| 扫描入口 | 用户选目录，插件扫整棵目录树 |
| 屏蔽路径 | 要支持（manifest 的 `ignorePaths`，每行一个，`#` 注释） |

## 六、关键 Bug 根因与修复（本次跑通核心总结）

1. **`video_only: True` 吃掉了 `.strm` 文件**：
   - **现象**：`_collect_files` 收到 0 个 strm。
   - **根因**：`files.scan` 开启了 `"video_only": True`。`.strm` 是流媒体 URL 文本文件而非视频容器，被 MT 宿主扫描器直接过滤。
   - **修复**：将 `_start_scan` 中的 `"video_only": True` 改为 `"video_only": False`。

2. **`tasks.wait` 报错 `input 不符合声明的 Schema`**：
   - **现象**：挂载等待失败，直接触发错误 fallback。
   - **根因**：原代码在 `completion` 字典中加入了自定义的 `selections` 并且未传 `"input": {}`，违反了 MT continuation action 的 schema 校验。
   - **修复**：按官方标准契约声明 `comp = {"action": "dup-collect", "input": {}}`。

3. **`FLOW_WAITING: 登记完成动作后请返回结果并释放工作进程`**：
   - **现象**：`tasks.wait` 完成后流程失败。
   - **根因**：在调用 `ctx.mt.tasks.wait` 后紧接着调用了 `ctx.mt.log(...)`。MT 宿主铁律：一旦注册等待，宿主即将当前 flow 置为等待态，此时严禁再调用任何 SDK 操作，必须立即 `return {"waiting": True}` 释放工作进程。
   - **修复**：日志提前在 `tasks.wait` 之前打印，调用 `tasks.wait` 之后直接返回 `{"waiting": True}`。

4. **收集时相对路径写错**：
   - **根因**：`collect` 收集文件名并按作品分组时，`by_work.setdefault(work, []).append({"rel": name, "name": name})` 将 `rel` 错写为 `name`，导致后续相对路径失效。
   - **修复**：修正为 `{"rel": rel, "name": name}`。

5. **评分公式模式 10 倍放大与 MT 官方规则彻底对齐**：
   - **文档依据**：https://murongyun8.github.io/MediaTidy-Wiki/features/rules.html#质量评分规则
   - **对齐规范**：
     - `总分 = Σ（维度权重 × 维度位置分）`
     - 优先级列表共 N 项时：第 1 项位置分为 10，第 2 项为 10*(N-1)/N，最后一项为 10/N，未命中为 0。
     - 维度得分 = `10 * (N - idx) / N * weight`。
     - 理论满分 `max_score` 对齐为 `sum(10 * weight)`。
     - 码率数值对数映射到位置分 0~10。
     - 取消自行硬编码 8.0 门槛，全面遵从 MT 规则原生 `minScoreDiff`。

6. **真实后缀读取与 ISO 槽位隔离**：
   - 读取 `.strm` 文件首行提取真实媒体文件后缀（如 `.iso`）。
   - 具有 ISO 槽位的整理方案将 ISO 版本隔离为独立槽位，不同槽位互不判重洗版，原盘保护成功。

7. **Fast Path 极速本地扫描落地**：
   - 针对 14w strm 耗时问题，优先走本地挂载直扫路径（Fast Path），实测 86 个作品目录 0.01 秒，数千文件亚秒级完成，大幅提升查重响应速度。

5. **沙箱环境打包工具链（`tools/pack_local.py`）**：
   - **根因**：由于安全策略 `NoNewPrivs: 1` 限制，宿主下无法使用 `su hua` 提权运行 Docker。而插件本身是 0 外部依赖，`uv.lock` 是静态的。
   - **方案**：编写纯 Python 的 `tools/pack_local.py`，根据 `pyproject.toml` 中的 include 配置直接在本地打包出合规的 zip，然后通过 HTTP API (`tools/deploy.py`) 直接部署。

### 安装 / 启用
- `config` 项**必须有 `default`**，否则 `install` 静默失败，`installJob.status=failed`、
  stage「安装未完成，原构建保留」，error 只有一句没用的话。
- `config` 项**不能有** `placeholder` / `minimum` / `maximum` / `description`；
  顶层 config **不支持** `type: "profile"` / `"select"`。
- `default: null` 非法。
- 插件**必须带 `ui/icon.png`**。
- `uv.lock` 必须在容器内（CPython 3.12.12 + uv 0.6.7）生成。
- 官方 `pack.py:56` 断言 `uv --version` 以 `"uv 0.6.7 "` 开头，实际输出是 `uv 0.6.7`（无尾随空格）——
  **官方 checker 自身的 bug**，所以用 `tools/pack_manual.py` 绕开。
- `pyproject.toml` 必须写 `[tool.mt-plugin].include = ["plugin.py","plugin.json","pyproject.toml","uv.lock","core","ui"]`，
  否则 `core/` 不会被打进包。
- `requires-python` 必须是 `">=3.12,<3.13"` 或 `"==3.12.*"`。
- `Plugin` 类要 `class Plugin(PluginBase)` 继承，**不是装饰器**。

### 授权
- `install` 的 `grants` **只传权限布尔** `{perm: True}`；多传 `capabilities`/`roots` 会让整次安装被拒。
- 启用必须 `PUT /api/plugins/<id>` 且 `enabled` + `config` + `grants` **三个字段同时给**；
  只传 `enabled` 会把 grants 清空，之后 `rules.list` 全报「插件没有此能力或资源的授权」。
- `grants.capabilities` 里**只能放 manifest 声明过的权限**，多一个就 403。
- `grants.roots` 是对象数组且要显式 `read: true`；
  路径必须是**容器内路径** —— 容器里是 `/strm`，宿主的 `/vol1/1000/strm` 不存在。

### 通道 / 返回值
- action 入口是 `POST /api/plugins/{id}/runs`，body 字段是 **`action`**（不是 `actionId`），
  选择项字段是 **`selections`**（不是 `files`）。
- action 的返回值宿主只认 **`{"waiting": bool}`**，别自作主张塞 `ok`/`error`/`message`。
- `tasks.wait` 入参只有 `refs`（数组）+ `completion{action, selections?, input?}`，
  `additionalProperties: false` —— **多一个没声明的键就报「input 不符合声明的 Schema」**；
  `completion.selections` 每项也只能有 `rootId` + `path`。
- `ctx.mt.log` 的级别只有 `debug/info/warn/error`，**没有 `warning`**。
- `inputSchema` 的 `additionalProperties` 必须是 `true`，宿主会把整个 envelope 传进来。

### UI
- `ui.Card(ui.Text(...))` —— **children 是位置参数**；写 `children=[...]` 会被塞进 props，
  宿主按属性白名单校验时判非法，`/ui` 直接 400。
- `Card` 合法属性只有 `title/description/visible/disabled`。
- `Table.columns` 每项**只能有 `label` 和 `cells`**，多一个 `field` 就 400；
  `source` 必须是页面上真实存在的 ref 或字面量 list。
- `Button.variant` 合法枚举里**没有 `primary`**。
- 校验器：`/tmp/uicheck.py`（按 `ui-registry.json` 逐节点校验），过一遍再部署。

### 配额 / 性能
- **`files.list` 每次运行只有 500 次配额**。绝不能逐目录递归 ——
  对选中目录直接发一次 `files.scan`（`maxScanFiles=10000`），递归交给宿主。

### 环境
- `hua` 用户**穿不过** `/vol1/@appshare/fn-deepseek-harness/日常`（`drwx------`），
  要给 hua 的文件必须先 `cp /tmp/...` 再 `chmod -R a+rX`。
- `su hua -c` 会把 `Password:` 混进 stdout，用 `> /tmp/x.txt 2>/dev/null` 再读文件，
  **不要** `grep -v Password`（会把正常结果一起吞掉）。
- 容器内**没有 `requests`**、没有 `ps`、没有 `strings`；诊断脚本用 `urllib`。
- 插件解包目录：`mediatidy:/app/data/plugins/packages/<包hash>/`；
  venv：`mediatidy:/app/data/plugins/environments/<instanceId>/<包hash>/`。
- 重新安装会新建 instanceId，旧的不会复用。

## 六、最新重要特性（已验证跑通）

1. **原生评分规则与门槛继承（绝无写死门槛）**：
   - 彻底移除了代码内硬编码的 `8.0` 门槛。
   - 优先通过 `rules.effective` 或 `organize.profiles` 动态读取 MT 规则的原生 `minScoreDiff`。
   - 规则设多少就是多少，规则没设门槛则为 0.0（只要有分差就判定，平分则交人工）。

2. **整理方案（Profile）与评分规则（Rule）下拉选择**：
   - 部署脚本 `deploy.py` 自动获取系统所有整理方案 ID 赋予权限。
   - 插件界面提供「选择整理方案」与「选择评分规则」下拉框，支持用户自定义搭配或自动匹配。

3. **读取 STRM 内容识别真实扩展名与槽位隔离**：
   - 扫描候选作品目录后，自动读取每个 `.strm` 文件首行，提取出真实文件扩展名（如 `.iso`, `.mkv`, `.mp4` 等）。
   - 严格遵循 MT 质量规则中配置的 `slots`（如 `ISO` 槽位：匹配 `file_extension: ["iso"]`；`normal` 槽位：匹配分辨率）。
   - 落在不同槽位的版本（例如原盘 ISO 与高清 MKV）各自独占槽位，**绝对不会互相误判为重复洗版**。
   - 只有落在相同槽位内的多版本，才会比对分差判定洗版。

5. **流程规范与极致性能引擎（Fast Path，14w 文件仅需约 10 秒）**：
   - **重申规范**：只在同一个电影目录或同一个剧集目录内部找重复；连集包重叠不处理；电影才读 strm 首行确定 ISO 槽位，剧集完全不读内容。
   - **双引擎架构**：
     - **Fast Path（本地极速引擎）**：优先通过容器内本地挂载点（`/strm`）执行目录树遍历。9200 个剧集文件仅需 0.1 秒扫描、0.7 秒完成季集分析；2100 个电影文件仅需 0.13 秒完成全量查重与首行 ISO 判定。按此速度 14 万个 strm 只需约 10 秒，彻底解决之前通过 HTTP 一页 100 条翻页导致的耗时超长与配额打满问题。
     - **Slow Path（降级引擎）**：本地路径不存在时无缝退回 `files.scan` + `tasks.wait`。
   - **轻量 I/O 原则**：
     - 单作品目录下 strm 数量 < 2 的直接跳过；
     - 剧集绝对不读取文件内容；
     - 电影仅在初筛发现该电影作品目录下存在 >= 2 个 strm 时，才读取其首行识别真实后缀与 ISO 槽位，最大限度减少文件 I/O。
