## 0. 一句话定位

**MT 整理之后的清扫环节。** 盯住 MT 整理不掉的「未识别目录」，用本地 sha1 归约库比对：
**命中 = 已整理过 → 删掉网盘上的原始媒体文件；未命中 = 原地保留，交给 AI 识别后由 MT 整理。**
strm 只用来扩充 sha1 库，从不碰 strm 文件本身。

> 注意：这不是「MT 整理之前过滤一遍」，而是**处理 MT 整理之后的未识别目录**。

### 1.1 设置为什么能「保存」

UI v2 里 `Input(bind="config.x")` / `FilePicker` / `ProfilePicker` 的 `bind` **只是样式绑定**，
宿主不会因为用户在框里打字就落库；`bind="state.x"` 才有语义，但只活在当前页面会话里。
所以「目录和整理方案的选取和保存」必须靠显式 action 把值写进插件存储：

- `save-flow-settings` → 键 `srcRoot/profileId/aiReview/cronExpr/autoExecute/maxDepth/maxDelete/cleanEmpty`
- `save-lib-settings` → 键 `mtDbPath/strmRoots/historyPath`
- `ai-sha1-settings` → 键 `profileId/review/instructions/prompt`
- 实现在 `core/settings.py`（`apply_settings` / `load_settings` / `save_settings`），存储在 storage KV 键 `settings`。
- **只改 payload 里出现的键**，不会因保存 A 区块而清空 B 区块。
- 页面用 `state.setdefault(k, ui.ref("query.overview.data.cfg." + k))` 回显上次保存的值。

`_cfg()` 三层合并，**后者覆盖前者**：`DEFAULT_CONFIG` → 清单配置（跳过空值）→ **页面保存的设置**。
让页面设置压过清单配置，是因为用户在页面上改了就该生效。

### 1.2 手动 sha1 匹配

「AI 识别」Tab 里的两条按钮：

- `🔎 直接比对库里有没有（只出结果）` → 复用 `dry-run`（会冻结快照，不动任何文件）
- `🤖 比对 + AI 再核对一遍命中项` → `sha1-match-recognize`

后者故意**不带整理方案**（`profileId=""`）：`_organize_items` 里识别为 `identify_only`，
只做识别、不提交整理，避免人工复核阶段误动媒体库。
它取快照里的**全部**文件（`batchAll=True`），而不是只取未命中的 keep 作品 ——
因为复核场景正是要连命中的（库里见过 = 已整理过）一起看。

## 2. 运行流程（一次 Job）

```
[0] 触发     手动按钮 / MT 插件定时器（triggers.schedules）
     ↓
[1] 扫描      遍历源目录，把每个文件的 path / name / ref / sha1 / size / rootId
              冻进「本批快照」（KV key = batch）。快照一旦生成，本批边界就固定了。
     ↓
[2] 比对      按「作品」聚合，视频逐个查归约库
     ↓
[3] 删除      命中作品 → 删整个作品文件夹；未命中/混合 → 原地保留，绝不搬走
     ↓       （删除后清理源目录内变空的父目录，见 §2.4）
[4] AI 识别   只读快照里的未命中文件（不重新扫云盘），走资料搜索识别身份
     ↓
[5] 整理      识别成功 → 提交 MT 整理方案（默认「阿里秒传」）
```

### 2.1 批次快照冻结（关键设计）

用户要求：「流程线上扫描到一批文件后，先进行 sha1 比对删除，剩余的再 AI 识别。**不能流程时间变长了，被新进的文件插队**到直接 AI 识别」。

实现方式：

- `_compare(..., snapshot=True)` 在扫描时把每个文件冻进 `KV_BATCH`，含 `path/name/ref/sha1/size/rootId`。
- AI 识别的 `_batch_files(ctx)` **只读快照里 `keptWorks` 目录下的文件**，完全不看 `ctx.files`、也不重新扫云盘。
- 快照缺失 → `BATCH_MISSING`；快照里没文件 → `BATCH_EMPTY`。两种情况都直接报错，**不会退回去扫云盘把新文件带进来**。

### 2.2 判定粒度：以「作品文件夹」为单位

只有**视频文件**参与判定，附属文件（nfo / 字幕 / 海报 / theme.mp3）不参与、随作品整体动作。

- **整包删除条件**：作品内视频**全部命中**（0 个未命中）
- **混合作品**（部分命中）：整包**保留**，不删，交 AI 识别。UI 用 ⚠️ 单独列出
- **缺 sha1 的视频**：一律视为**未命中**（安全侧）
- 无视频的作品：标 `no-video`，不动
- 无法判定作品层的：标 `unrecognized`，不动

### 2.3 作品层自动探测（优先级 + 反向规则）

正向规则（依次尝试）：

1. 目录名含 `{tmdb-N}` / `{tvdb-N}` / `{imdb-ttN}`
2. 目录名匹配 `名字 (年份)` 或 `名字 (年份-年份)`
3. 内含 `Season N` / `Specials` / `S01` / `第1季` 子目录
4. 内含「发布目录」子目录（`1080p` / `WEB-DL` / `H265` / `DDP` / `S01E01` 等）
5. 直接含视频文件

反向规则（防止作品根被误判到内层）：

- 目录名本身像发布目录（含 `1080p` / `S01` / `WEB-DL`…）→ **不是**作品根，继续向上找
- 同一条文件链解析出多个作品候选时，**取最外层**，并把内层候选**合并**进外层
  （否则同一部剧会被拆成两条记录，季目录还可能被单独判成「全部命中」而整包删除）

实测验证：

| 目录结构 | 识别出的作品根 |
|---|---|
| `X (2020) {tmdb-1}/Season 1/E01.mkv` | `X (2020) {tmdb-1}` ✅ |
| `The.Cleaning.Lady/The.Cleaning.Lady.S01.1080p.WEB-DL/E01.mkv` | `The.Cleaning.Lady` ✅（修复前误判为内层） |
| `作品B (2018)/BDMV/00001.m2ts` | `作品B (2018)` ✅ |
| 源根下 `散落片.mkv` | 单文件自成一体 ✅ |

### 2.4 空目录清理的两条硬边界

用户要求：「sha1 比对目录内 100% 直接把空目录删了，**但是不能再往上删除**」。

`clean_empty_parents(ctx, deleted_paths, src_root, keep_paths)`：

1. **绝不越过 `src_root`** —— 源目录本身及其上级永不删除
2. **绝不越过 keep 作品根** —— 里面是要交给 AI 识别的作品，即使此刻空着也不动

实测边界：

| 删除的文件 | 清理结果 |
|---|---|
| `/a/b/x (2020)/f.mkv` | 只清 `/a/b/x (2020)` ✅ |
| `/a/b/x/f.mkv` | 清 `/a/b/x` ✅ |
| `/a/b/f.mkv` | 什么都不清（源目录绝不动）✅ |
| `/a/b/keep (2020)/f.mkv` | 不清（keep 作品根）✅ |
| `/a/b/keep (2020)/S1/e.mkv` | 不清 ✅ |

### 2.5 取消搬迁目录

用户 2026-10-29：「这样就不用再搞个转移目录」。

`dstRoot` / `maxMove` / `plan_targets()` / `_move_with_rename()` 全部删除。未命中的作品**原地不动**，直接进入 AI 识别。

## 2.9 归约库与设置必须跨「卸载→重装」存活（2026-10-30 修正）

**问题**：MT 每次卸载重装插件都会生成新的 `instanceId`，
`ctx.data_dir` → `plugins/data/<instanceId>/`，storage KV 也绑定新实例。
结果开发期每重装一次，80 万条的库就清零一次，要花 130 秒重建。

**修法**：库与设置都落到容器内**固定路径**，不再依赖实例目录。

| 数据 | 路径 | 兜底 |
|---|---|---|
| 归约库 | `/app/data/plugins/data/.media.sweep/sha1lib.sqlite3` | 不可写时退回 `ctx.data_dir` |
| 页面设置 | `/app/data/plugins/data/.media.sweep/settings.json` | 同上 |

- `plugin.py: _lib_path(ctx)` 逐个探测候选路径的可写性（写一个 `.writetest` 再删），选第一个可用的。
- `plugin.py: migrate_library(ctx)` 在 `on_init` 里跑：固定路径还不存在、而当前实例目录里有库时，
  把 `sha1lib.sqlite3` 连同 `-wal` / `-shm` 一起复制过去（幂等，只做一次）。
- `core/settings.py` 改成**双写**：先写 JSON 文件（跨重装），再写 storage KV（当前会话）。
  读的时候「文件 → KV」合并，老版本只存在 KV 里的设置也不会丢。
- AI 识别分区的 `_sha1_gate` 通过 `Plugin.library_path(ctx)` 取路径，
  不再自己拼 `ctx.data_dir`，否则手动 sha1 过滤会读到一个空库。

**真机验证**：`reinstall` 两次后 `overview.total` 恒为 **796,252**、`sets` 11 项完整回读。

## 3. 数据：sha1 归约库

**只存 sha1 值**，不存其他字段（用户明确要求）。存储位置：插件 `data_dir` 里的 SQLite（WAL 模式）。

不用 MT storage KV：硬约束 32 MiB / 10,000 键 / 单值 256 KiB，装不下 79 万条。

### 3.1 三个来源与分工

| 来源 | 常量 | 定位 | 实测条数 |
|---|---|---|---|
| **MT FF 缓存** | `SRC_MT_CACHE=1` | **长期主力，每次增量同步** | 400,000 |
| 历史导入（txt/csv） | `SRC_HISTORY=2` | 一次性（用户自己的旧库） | 0（本期未用） |
| **STRM 扫描** | `SRC_STRM=4` | 一次性（初期扩充） | 396,226 |
| **合并去重** | — | — | **796,226** |

### 3.2 MT FF 缓存为什么必须「双路增量」

`organize_file_probe_cache` **锁死 40 万行**，存满后新增只会替换最旧的（用户 2026-10-29 说明）。

实测：表内 40 万行，但 rowid 跨度 1~452,952 —— 历史删过 5.3 万行，**空洞从 rowid 29 就开始并散布全表**，不是只砍尾部。所以纯 rowid 游标会漏掉「后插入、先被淘汰」的行。实现双路：

- **路 A（主路）**：`SELECT sha1, created_at WHERE created_at > ? ORDER BY created_at`，参数带 30 秒 overlap。走索引，0.002 秒。
- **路 B（兜底）**：全表拉 40 万个 sha1 与本地库求差集，补齐「曾漏同步且尚未被淘汰」的行。2.5 秒。
- 游标只在新数据**全部落库后**才推进；时间串解析失败时静默回退全量，避免漏数据。

**实测日常增量：4.8 秒**（取到 83 行、新增 44）。

### 3.3 STRM 扫描

- 目录：`/strm/云盘影视`（569,770 个 .strm）+ `/strm/shareStrm`（700,705 个）= 1,270,604
- 分享型 strm 内容是 `http://.../api/shareVideoPlayUrl?...&sha1=CD62F840...&fileName=...`，**URL 直接带 `sha1=`**，读文本正则提取即可，无需任何云盘 API
- 实测：http 带 sha1 1,256,081 / http 无 sha1 1,011 / 非 http 13,512；**新增 396,226 条**
- 完整扫完才置 `META_STRM_DONE="1"`，下次自动跳过（一次性动作）

### 3.4 安全底线

**库为空时禁止执行删除。** 防止「库没建好就把整个目录清空」。

## 4. 云盘访问：MT 原生 `files.*`（不用 CD2）

用户 2026-10-29：「mt不是有查询sha1的接口，为什么还要走cd2? mt的本地缓存ff数据是可以导出的」。

已彻底移除 CD2 gRPC（`grpcio` / `protobuf` 依赖清零 → 插件**零第三方依赖**，安装 5 秒完成）。改为 `core/mtfs.py` 走 MT 原生文件 API：

| 能力 | MT 方法 | 说明 |
|---|---|---|
| 列目录 | `files.list(rootId, path, page)` | 按 `hasMore` 自动翻页 |
| 取 sha1 | `files.list` / `files.stat` 返回的 `sha1` | **只在 `storageType=cloud` 的根下的「文件」上填充**；目录没有该键 |
| 删除 | `files.delete(fileRef, recursive, idempotencyKey)` | 目录需 `recursive=True`；**幂等：路径不存在视为已删** |
| 移动 | `files.move(fileRef, destination:{rootId,path}, idempotencyKey)` | `destination` 是**对象**，不是字符串 |
| 等待任务 | `tasks.wait(refs=[...], completion={action, input})` | 用 `refs` 数组 |

**关键实测**：云盘根在 MT 侧叫 `小小玻珠`（不是 `115open`）；`files.roots()` 返回项**没有 path 字段**。

## 5. AI 识别（吸收自 official.ai-organize，已改造）

### 5.1 三级降级（核心改造）

原版硬依赖「服务商原生网页搜索」，而用户的反代 Gemini 不透传搜索元数据 → 必然失败。

| 级别 | 方式 | 状态 |
|---|---|---|
| 1 | `ai.chat(single_request=True, native_web_search=True)` | ❌ 本机不可用（反代不透传搜索记录） |
| 2 | **`ai.web.search(query)` + `ai.chat`** | ✅ **可用，主路线** |
| 3 | 纯 `ai.chat` 按文件名识别 | 兜底，标记为未搜索 |

降级判断的关键修正：`AI_NATIVE_SEARCH_NOT_PERFORMED` **必须**降级，不能当成硬失败（它恰恰是「该降级了」的信号）。

### 5.2 TMDB ID 从搜索结果 URL 里抽，不靠 AI 填

实测 AI 自己填的 TMDB ID 基本是编的（`The Cleaning Lady` 给了 119051，实际是「星期三」）。改为：

- 用 `tmdb_source(url)` 从 `ai.web.search` 返回的 URL 抽 `(kind, id)`，如 `themoviedb.org/tv/534271-...` → `(tv, 534271)`
- 用 URL slug 与作品名做归一化匹配，命中则**替换** AI 给的 ID，标记 `idFrom="search-url"`
- 真机结果：`The Cleaning Lady → 534271 (tv)`、`A Royal Affair → 88273`、`洪兴仔之江湖大风暴 → 118416`

### 5.3 字段容错

AI 会换字段名、换大小写、换 ID 形态。`normalize_identity()` 统一处理：

- 类型：`type` / `media_type` / `media` / `category`，值大小写归一，`episode` / `series` / `show` / `剧集` → `tv`
- 原文名：`original_title` / `titleOriginal` / `titleEn` / `titleZh` / `titleEnUs`
- 年份：`releaseYear` / `firstAirYear` / `premiereYear`
- ID：只接受 `movie/88273`、`tv/534271`、`tmdb-118416` 形态

### 5.4 不强行识别（用户 2026-10-29 要求）

用户：「有些垃圾命名的资源，**没必要强行识别，准确率最高**」。

- 置信度 `low` / `very low` / `uncertain` / `unknown` / `低` / `很低` / `不确定`，或数值 < 0.7 → **直接跳过**，文件保留原位等人工确认
- 没有 TMDB ID → 跳过，不自动搜索 ID
- `year` / `originalTitle` 不再强求 AI 给（它经常不给）→ 由 `tmdb.detail` 核对后**回填**

### 5.5 AI 回答必须走原文重试

模型偶尔无视 JSON 契约改答 Markdown 表格。处理方式：

- **绝不解析 Markdown 表格语义**（猜错会整理错作品）
- 把模型自己的回答甩回去（`previousReplyNotJson`），明确要求「只输出 JSON」再要一次
- 再失败就判该批无效，让用户重试或在界面里看原文

### 6.1 UI v2 实现踩坑（都会静默失败）

| 问题 | 现象 | 修法 |
|---|---|---|
| `ui.Tab` 缺 `id` | **内容区永远空白，宿主不报错** | 每个 Tab 必须带 `id` |
| `Tabs` 缺 `bind` | `INVALID_UI_PAGE: content[1].props.bind: 缺少可写绑定` | 配 `bind="state.activeTab"` + `state` |
| 容器组件带 `id` | `props.id: 不支持此属性` | 只有 `Tab` 允许 `id` |
| `Table` 用 `rows=` | `props.rows: 不支持此属性` | 用 `source=` |
| `Button` 用 `text=` | `props.text: 不支持此属性` | 用 `label=` |
| `Alert` 用 `label=` | 同上 | 用 `text=` |
| 表达式嵌套过深 | 只报顶层 `page: JSON 无效`，不给路径 | `maxDepth:12` = **组件树深度 + 表达式深度相加** |
| `Table` 单列 cells 过多 | `必须为包含 0–20 项的数组` | 单列 cells ≤ 20 |
| `Input` 用 `text=` | 不显示 | 用 `bind=` |

---

## 7. 定时

`plugin.json` 声明 `triggers: [{"key":"sha1-dedup-job","type":"schedule","action":"run-job"}]`，
`on_init` 里 `ctx.mt.triggers.schedules.upsert(declaration_key=..., cron=..., kind="cron")`。
五段 Cron 顺序为 **分 时 日 月 星期**。**新建默认暂停**，需用户在界面里启用。

## 8. 明确不做（v1 范围外）

- 不搬迁文件（已取消目标目录）
- 不处理 strm 文件本身（strm 只用来扩充 sha1 库）
- 不自动删除源目录本身
- 不在 AI 置信度不足时强行识别
- 不解析 Markdown 表格来猜识别结果

### 9.3 MT 平台坑位汇总（供后续插件复用）

1. `ui.Tab` 必须带 `id`，否则内容区永远空白且无任何报错
2. `Tabs` 必须配 `bind` + `state`
3. query 必须在 manifest 声明 `inputSchema`，否则前端带参请求 400
4. `maxDepth:12` 是「组件树深度 + 表达式深度」相加
5. `Table` 单列 `cells` 上限 20 项
6. `POST /api/plugins/cleanup` 可清旧包（`PLUGIN_PACKAGE_LIMIT` 唯一解）
7. `ctx.mt.log` **没有 `warn` 级别**
8. `grants.profileIds` 不授权 → `organize.profiles()` 返回空 list
9. `grants.roots` 必须是**对象数组**（`{read,write,delete,id,name,path,storageType}`），不是字符串
10. `config` 里每个 key 必须在 `configSchema` 声明，否则安装静默失败（真因只在 `plugin_records.installJob.body.error`）
11. MT 业务忙时 `tmdb.detail` / `files.list` / `organize.manual.run` 统一报「操作未完成」（`OPERATION_FAILED`），需退避重试
12. 打包 zip 内路径必须用 `relative_to(root).as_posix()`，用绝对路径会缺 `ui/icon.png` → 安装静默失败
13. `pyproject.toml` 的 `[project].name/version` 必须与 `uv.lock` 的 `[[package]]` 同步，否则安装卡在 stage 永不完成
14. `plugin.json.entry` 必须字面为 `plugin.py:Plugin`
15. handler 签名是 `(self, input, ctx)` —— input 在前，ctx 在后
16. 官方 PyPI 的 `grpcio` 索引页在本网络拉不动 → uv 解析卡死（这就是坚持零第三方依赖的原因）
